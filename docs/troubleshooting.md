# Частые проблемы и что с ними делать

## Контейнер умер с кодом 137 / `Exited (137)`

137 = процесс убит из-за нехватки памяти (OOM). Это штатная защита: у каждого
сервиса стоит лимит, чтобы прожорливый процесс не утащил за собой остальные.
Данные при этом целы.

Что делать:
1. `docker stats` — посмотри, кто сколько ест.
2. Если это твой код — ты, скорее всего, тянешь сырые события в pandas.
   Не надо: агрегируй в ClickHouse SQL-ем, в Python забирай уже маленький результат.
3. Если памяти мало в принципе — проверь, сколько выделено докеру: `make check`.
   Поднять: Mac — Docker Desktop → Settings → Resources → Memory;
   Windows — `%UserProfile%\.wslconfig` → `[wsl2]` → `memory=8GB`, затем `wsl --shutdown`.

## Всё дико тормозит, вентилятор воет

Памяти впритык, система свопит. См. пункт выше: подними лимит докера.
Также закрой лишние приложения-тяжеловесы.

## `mounts denied: The path ... is not shared from the host`

Проект склонирован в папку, которую Docker Desktop не расшаривает (например,
`/Applications` на Mac). Решения: склонируй проект в домашнюю папку (`~/...`) —
это правильный вариант; либо добавь путь в Docker Desktop → Settings → Resources →
File Sharing.

## Запрос в ClickHouse падает с `MEMORY_LIMIT_EXCEEDED`

На один запрос стоит лимит 512 МБ. Почти всегда это случайное декартово
произведение (JOIN без условия) или `SELECT *` по всей таблице. Проверь условия
JOIN и добавь фильтр по `event_date` — таблица партиционирована по месяцам,
фильтр по дате читает только нужные куски.

## DataGrip: ClickHouse падает с «Unknown and unmapped config properties: [databaseTerm, session_id]»

Несовместимость свежего ClickHouse-драйвера с твоей версией DataGrip: новый
драйвер убрал свойства, которые DataGrip ему передаёт. Два способа починить:

Это не влияет ни на данные, ни на сервер — конфликт живёт целиком внутри IDE.
Два способа починить:

1. Выбрать более старую версию драйвера: окно Data Sources and Drivers →
   раздел **Drivers** в левой панели → **ClickHouse** → в блоке Driver Files
   кликни на синюю ссылку **«ver. X.Y.Z [stable]»** — откроется список версий,
   выбери **0.6.5** (любую 0.6.x) → OK → Test Connection.
2. Либо обнови сам DataGrip (Help → Check for Updates) — свежие сборки
   совместимы с новым драйвером.

Если возиться не хочется — DBeaver подключается без этих танцев (см. README, шаг 0.5).

## DataGrip/DBeaver подключается очень долго, хотя стек работает

Если `curl http://localhost:8123/ping` отвечает мгновенно, а Test Connection
в SQL-клиенте думает по 10–20 секунд — это тормозит Java на macOS, а не база:

1. Частая причина — имени твоего Mac нет в `/etc/hosts`, и JVM на каждом
   соединении подолгу резолвит его по сети. Лечится один раз (подставь своё
   имя машины из команды `hostname`):

   ```
   sudo sh -c 'printf "127.0.0.1\tИМЯ-ТВОЕГО-MAC.local\n::1\tИМЯ-ТВОЕГО-MAC.local\n" >> /etc/hosts'
   ```

   После этого перезапусти SQL-клиент.
2. Также помогает в настройках соединения писать `127.0.0.1` вместо `localhost`.
3. Первое подключение к базе всегда дольше: клиент сканирует метаданные всех
   таблиц (в статус-баре видно «Introspecting…»). Это одноразово — подожди.


## Генератор «молчит», событий не прибавляется

`docker compose logs -f generator`. При первом старте он несколько минут наливает
историю — это нормально, жди строку «история готова». Если упал — там же будет
traceback.

## Сплитовалка отвечает 503 «симуляция ещё не инициализирована»

Генератор ещё не закончил бэкфилл истории (см. пункт выше). Эксперимент можно
создать, но запустить — только когда появится виртуальное время (`GET /sim/now`).

## Порт занят (`port is already allocated`)

`make check` покажет, какие порты заняты. Чаще всего это параллельно запущенный
data-platform или второй запуск стека. Останови лишнее: `docker ps` → `docker stop <имя>`.

## Хочу начать с чистого листа

```
make reset   # удаляет ВСЕ данные: базы, историю, эксперименты
make up
```

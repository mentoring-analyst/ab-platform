# Финальный проект: полный цикл A/B-теста на инфраструктуре

Ты — аналитик команды главного экрана заказа. Команда хочет протестировать
новый способ показа цены: вместо диапазона ($14–20) — одна ориентировочная
цена ($17.29). Твоя задача — провести этот эксперимент от идеи до решения
на настоящей инфраструктуре: сплитовалка, поток событий, витрины, дашборд.

Контекст кейса, легенда и теория — в ноутбуке финального проекта.
Здесь — практические шаги на платформе.

## Этап 0. Подними платформу

```
make check
make up        # лёгкий профиль: Postgres + ClickHouse + сплитовалка + генератор
```

При первом старте генератор создаёт популяцию пользователей и наливает
~45 виртуальных дней истории (меньше минуты). Прогресс: `docker compose logs -f generator`.

Проверь, что живёшь:
- Админка сплитовалки: http://localhost:8000 (в шапке — текущее виртуальное время)
- API той же сплитовалки: http://localhost:8000/docs
- Подключись DataGrip/DBeaver к Postgres (localhost:5434) и ClickHouse (localhost:8123)

## Этап 1. Исследуй данные

В ClickHouse таблица `ab.events` — поток событий воронки:
`app_open → screen_view → tariff_select → order_confirm → trip_complete / order_cancelled`.

Ответь SQL-запросами:
1. Сколько активных пользователей в день? Как выглядит сезонность по часам и дням недели?
2. Какая конверсия `screen_view → order_confirm` по регионам?
3. Как распределено число поездок на пользователя? Почему среднее сильно больше медианы?
4. Как цена (`price_high` / `price_shown`) связана с конверсией в заказ?

## Этап 2. Карточка эксперимента

Заполни `templates/experiment_card.md`, открой Pull Request, пройди ревью ментора.
Без утверждённой карточки эксперимент не запускается.

## Этап 3. Размер выборки

Продакт просит: «хочу ловить эффект от 0.5 п.п.». Открой
`templates/sample_size_calculation.ipynb`, посчитай размер выборки калькулятором
и симуляциями, сверь с `POST /experiments/{code}/audience/preview` — и подготовь
продакту ответ: реализуемо ли это на нашем трафике, и если нет — какие есть варианты.

## Этап 4. Заведи и запусти эксперимент

В админке (http://localhost:8000 → «+ Эксперимент»):
1. Заполни форму: код `pricing_point_estimate`, варианты и доли трафика
   из утверждённой карточки. Доли — проценты от всего трафика аудитории:
   A 20% + B 20% значит, что эксперимент идёт на 40% трафика, остальные 60%
   в него не попадают. Подумай, зачем компании запускают эксперимент не на все 100%.
2. Отметь метрики и их роли: целевая, прокси, защитные. Своей метрики не хватает?
   Заведи её на вкладке «Метрики» — SQL-запрос по `ab.events` проверяется
   в ClickHouse прямо при сохранении.
3. На странице эксперимента нажми «Запустить». Генератор начнёт сплитовать
   пользователей при первом заходе (exposure) — набор аудитории постепенный.

Всё то же самое можно сделать через API (http://localhost:8000/docs) — в проде
эксперименты часто заводят именно так, из кода.

Проверь себя на странице эксперимента: группы наполняются? Фактические доли
соответствуют плану?

## Этап 5. Автоматизация и дашборд

```
make up-full   # + Airflow (localhost:8081) + Superset (localhost:8089), admin/admin
```

1. В Airflow включи DAG `ab_experiment_metrics` — он реплицирует абшницу в ClickHouse
   и считает дневные метрики в `ab.experiment_metrics_daily`. Прочитай его код:
   почему он идемпотентный? почему в нём нет `catchup` и `{{ ds }}`?
2. В Superset собери дашборд эксперимента по гайду `docs/superset_dashboard.md`:
   кривая набора аудитории, SRM-проверка, динамика метрик по дням.
   Этот дашборд смотрит продакт — подпиши всё человеческими словами.

## Этап 6. Дождись данных и прояви выдержку

При ускорении по умолчанию 1 виртуальный день = 10 минут. Две недели эксперимента —
около 2.5 часов реального времени. Подглядывать в метрики каждый день можно
(продакт так и будет делать), а вот принимать решение по третьему дню — нельзя.
Почему? Ответ должен быть в твоей карточке.

## Этап 7. Анализ и решение

Останови эксперимент (`POST /experiments/{code}/stop`), выгрузи данные SQL-ем
из ClickHouse и проведи анализ по ноутбуку финального проекта: sanity-checks,
SRM, статистические тесты по каждой метрике, выводы.

Сдай:
1. Заполненную карточку (обновлённую результатами) — PR в свой форк.
2. Ноутбук анализа с расчётами.
3. Скриншот дашборда.
4. Решение: раскатываем / не раскатываем / дорабатываем — с аргументами.

## Бонус-уровни

- Заведи и прогони A/A-тест: эксперимент с двумя одинаковыми группами.
  Что ожидаешь увидеть? Зачем компании гоняют A/A?
- Добавь третий вариант C (доли 34/33/33) и посмотри, что произойдёт с защитными
  метриками. Внимательно смотри на `cancel_rate`, прежде чем радоваться конверсии.
- Напиши свою метрику через `POST /metrics` (например, средний чек поездки)
  и подключи её к эксперименту.
